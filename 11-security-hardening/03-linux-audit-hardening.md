# Linux Audit and Hardening

A reference guide to detecting what's actually happening on a Linux system — kernel-level audit logging with `auditd`, file integrity monitoring, and the benchmark frameworks that operationalize hardening at scale.

---

## 🧱 Why Audit Logging Is a Distinct Layer

Earlier guides cover *configuring* a secure system — permissions, sudo scoping, firewall rules, SSH hardening. **Auditing** answers a different question: **given that configuration, what is actually happening on this system right now, and can I prove it after the fact?** A perfectly configured system with no audit trail still leaves you unable to answer "who did this, and when" after an incident — auditing is what turns a security configuration into something verifiable and forensically useful.

This connects directly to the **secure baseline drift** concept from the *Linux Security Principles* guide: a baseline only stays meaningful if something is actually watching for departures from it over time, rather than just being correct at the moment it was set.

## 🔍 `auditd` — Kernel-Level Audit Logging

### What `auditd` Actually Does

`auditd` is a userspace daemon that receives and records audit events generated by the **Linux kernel's audit subsystem** — a fundamentally lower-level, more comprehensive source of activity data than application logs or even `journald`'s service-level logging (see the *Logs and journald* guide). It can record system calls, file access, authentication events, and administrative actions, each tagged with the responsible user, process, and exact action taken.

### How This Differs from journald/syslog

| | `journald` / syslog | `auditd` |
|---|---|---|
| Source of events | Applications and services choosing to log something | The KERNEL itself, observing actual system calls/actions |
| Primary purpose | General operational logging, troubleshooting | Security-focused, forensic, compliance-oriented record-keeping |
| Granularity | Whatever an application decided to log | Can track specific file access, specific syscalls, regardless of whether any application "logs" it |
| Tamper resistance | Standard log file/journal protections | Designed with stronger integrity guarantees in mind (see below) |

> **Practical implication:** if you need to know "did anyone read or modify this specific file, by whom, when" — and the application that owns that file doesn't itself log file access — `journald`/application logs simply won't have that information. `auditd`, with the right rule in place, will.

### Installing and Starting `auditd`

```bash
sudo apt install auditd audispd-plugins      # Debian/Ubuntu
sudo dnf install audit                          # RHEL/Fedora — often installed by default
sudo systemctl enable --now auditd
sudo systemctl status auditd
```

### Audit Rules: What Gets Watched

Rules are defined in `/etc/audit/rules.d/` and loaded via `auditctl`.

```bash
sudo auditctl -l                  # list currently active rules
```

### Watching a Specific File

```bash
sudo auditctl -w /etc/passwd -p wa -k passwd_changes
```

| Flag | Meaning |
|---|---|
| `-w` | Watch this specific path |
| `-p` | Permission types to watch: `r` (read), `w` (write), `x` (execute), `a` (attribute change) |
| `-k` | A key/label for this rule — makes searching results easier later |

### Watching System Calls Directly

A more powerful (and more advanced) capability: tracking specific syscalls regardless of which file or program triggers them.

```bash
sudo auditctl -a always,exit -F arch=b64 -S execve -k process_execution
```

This tracks every program execution (`execve`) system-wide — useful for answering "what programs have actually been run on this system," independent of whether any specific application chose to log that.

### Making Rules Persistent

Rules added with `auditctl` directly are **temporary**, lost on reboot — for persistence, define them in a rules file:

```bash
sudo nano /etc/audit/rules.d/audit.rules
```

```
-w /etc/passwd -p wa -k passwd_changes
-w /etc/shadow -p wa -k shadow_changes
-w /etc/sudoers -p wa -k sudoers_changes
-a always,exit -F arch=b64 -S execve -k process_execution
```

```bash
sudo augenrules --load        # regenerate and load rules from rules.d/ files
```

### Querying Audit Logs: `ausearch` and `aureport`

Raw `/var/log/audit/audit.log` is technically readable but verbose and not meant for direct human consumption — `ausearch` and `aureport` are the intended query tools.

```bash
sudo ausearch -k passwd_changes              # search by the key/label set in the rule
sudo ausearch -k sudoers_changes --start today
sudo ausearch -ui 1001                          # search by a specific UID (see the User Account Basics guide)
sudo ausearch -p 1234                            # search by PID
```

```bash
sudo aureport --summary               # high-level summary across all event types
sudo aureport -au                       # authentication-specific report
sudo aureport -x                          # executable-execution report
```

### A Practical Hardening Set of Rules

A commonly recommended baseline rule set, watching the files most relevant to privilege and account security covered across earlier guides:

```
-w /etc/passwd -p wa -k identity                 # see User Account Basics
-w /etc/shadow -p wa -k identity                   # see Authentication and Passwords
-w /etc/group -p wa -k identity                      # see Group Management
-w /etc/sudoers -p wa -k privilege_escalation          # see sudo and Privilege Management
-w /etc/sudoers.d/ -p wa -k privilege_escalation
-w /etc/ssh/sshd_config -p wa -k sshd_config             # see Firewall Hardening / User Security
```

> **Tip:** Watching these specific files directly addresses a real gap — file permissions (see the *Permissions and Modes* guide) control *who can* modify them, but say nothing about *who actually did*, or *when*. Auditing closes that visibility gap.

## 🗂️ File Integrity Monitoring

### The Core Idea

File integrity monitoring (FIM) periodically checks whether files that **shouldn't normally change** — system binaries, configuration files, libraries — have actually changed since a known-good baseline was recorded. An unexpected change to `/usr/bin/ls` or `/etc/passwd` outside of a deliberate, known update is a strong signal of compromise or unauthorized modification.

### Why This Complements, Not Duplicates, Package Verification

The *Package Security and Updates* guide covers `debsums`/`rpm -V`, which check installed files against what the **package manager** recorded at install time. FIM tools serve a similar purpose but are typically:
- **Distribution-independent** — not relying on package manager metadata specifically.
- **Continuously scheduled** — checking on an ongoing basis, not just on demand.
- **Broader in scope** — often configured to watch files beyond what any package "owns," including custom configs and application data.

### `AIDE` (Advanced Intrusion Detection Environment)

A widely used, distribution-agnostic FIM tool.

```bash
sudo apt install aide        # Debian/Ubuntu
sudo dnf install aide          # RHEL/Fedora
```

### Initializing the Baseline Database

```bash
sudo aideinit                          # Debian/Ubuntu convenience wrapper
# or, more manually:
sudo aide --init
sudo cp /var/lib/aide/aide.db.new /var/lib/aide/aide.db
```

> **Critical timing consideration:** the baseline must be created on a system you're confident is **already clean** — if a compromise happened before the baseline was recorded, AIDE will treat the compromised state as "normal" and never flag it. This is why FIM is most valuable when set up as part of initial provisioning (see the *secure baseline* concept in the *Linux Security Principles* guide), not retrofitted onto a system that's already been running, unmonitored, for a long time.

### Configuring What to Watch

```bash
sudo nano /etc/aide/aide.conf
```

```
/etc        p+i+u+g+sha256
/bin        p+i+u+g+sha256
/sbin       p+i+u+g+sha256
/usr/bin    p+i+u+g+sha256
!/var/log     # exclude — logs are EXPECTED to change constantly
```

| Attribute | Meaning |
|---|---|
| `p` | Permissions |
| `i` | Inode number |
| `u` | Owner (user) |
| `g` | Owner (group) |
| `sha256` | Cryptographic checksum of file contents |

### Running a Check

```bash
sudo aide --check
```

```
AIDE found differences between database and filesystem!!
Summary:
  Total number of entries:    45213
  Added entries:               2
  Removed entries:             0
  Changed entries:             1

Changed entries:
f  ... : /etc/passwd
```

### Scheduling Regular Checks

```bash
sudo crontab -e
```

```
0 3 * * * /usr/bin/aide --check | mail -s "AIDE Report - $(hostname)" admin@example.com
```

> **Tip:** A FIM check that runs but nobody ever reviews provides limited value — pair scheduled checks with an actual alerting/notification mechanism, not just a log file no one looks at.

### Updating the Baseline After Legitimate Changes

After a deliberate, known-good change (a package upgrade, an intentional config edit), the baseline needs to be refreshed — otherwise every future check will keep flagging the same legitimate change as a "difference":

```bash
sudo aide --update
sudo cp /var/lib/aide/aide.db.new /var/lib/aide/aide.db
```

> ⚠️ **Caution:** Routinely accepting every flagged change without genuinely reviewing it first defeats the purpose of FIM entirely — the discipline of actually inspecting *why* something changed before updating the baseline is what makes the tool meaningful, rather than a checkbox exercise.

### Other Notable FIM Tools

| Tool | Notes |
|---|---|
| `Tripwire` | One of the original, well-established FIM tools; commercial and open-source editions exist |
| `Samhain` | Distributed FIM with centralized logging/reporting designed for multi-host environments |
| `OSSEC` / `Wazuh` | Broader host-based intrusion detection suites that include FIM as one component among many |

## 📋 Security Benchmarks and Hardening Frameworks

### Operationalizing What Earlier Guides Cover Conceptually

The *Linux Security Principles* guide introduced CIS Benchmarks and DISA STIGs at a conceptual level — this section covers actually **applying and auditing against** them.

### Scanning with OpenSCAP

```bash
sudo apt install openscap-scanner ssg-debian      # Debian/Ubuntu — package names vary by distro
sudo dnf install openscap-scanner scap-security-guide   # RHEL/Fedora
```

```bash
oscap info /usr/share/xml/scap/ssg/content/ssg-debian12-ds.xml      # see available profiles in a content file
```

```bash
sudo oscap xccdf eval \
    --profile xccdf_org.ssgproject.content_profile_cis_level1_server \
    --results results.xml \
    --report report.html \
    /usr/share/xml/scap/ssg/content/ssg-debian12-ds.xml
```

This evaluates the live system against a specific CIS Level 1 Server profile and produces a human-readable HTML report (`report.html`) detailing exactly which checks passed, failed, and why.

### Reading OpenSCAP Results

```
Title   Ensure SSH PermitRootLogin is disabled
Result  fail
Rule    xccdf_org.ssgproject.content_rule_sshd_disable_root_login
```

Each failed rule typically includes a clear remediation description — directly connecting back to specific configuration steps covered in the *Firewall Hardening* and *User Security* guides (in this example, the `PermitRootLogin no` setting).

### Automated Remediation (With Caution)

Many SCAP content sets support generating a remediation script or Ansible playbook directly from scan results:

```bash
sudo oscap xccdf generate fix --profile cis_level1_server --output remediation.sh ssg-debian12-ds.xml
```

> ⚠️ **Caution:** Automated remediation scripts apply many changes at once, some of which can break application functionality if applied blindly (e.g. disabling a protocol or service something genuinely depends on). Review generated remediation carefully, and test in a non-production environment first — treat it as a strong starting point, not a script to run unattended against a production system.

### Lynis — A Lighter-Weight Alternative

For a less formal, faster general security audit without needing to select/manage specific SCAP content:

```bash
sudo apt install lynis      # or: sudo dnf install lynis
sudo lynis audit system
```

```
[+] Authentication
------------------------------------
  - Checking for password aging...                            [ WARNING ]
  - Checking expiration of passwords...                         [ FOUND ]

Suggestions:
* Configure password aging for users with a shell [AUTH-9282]
```

> **Lynis vs. OpenSCAP:** Lynis gives quicker, more general-purpose findings with practical suggestions and is easier to run ad hoc; OpenSCAP/SCAP content provides formal, profile-based compliance scoring (CIS Level 1/2, specific STIGs) more suited to environments with actual compliance reporting requirements. Many environments use both — Lynis for frequent informal checks, OpenSCAP for periodic formal compliance verification.

## 🔄 Bringing It Together: A Continuous Audit/Hardening Cycle

```
1. Establish a baseline       → secure configuration (earlier guides) + AIDE database + audit rules
2. Continuously monitor        → auditd events, scheduled AIDE checks
3. Periodically scan formally    → OpenSCAP against CIS/STIG profiles, Lynis for general findings
4. Review and remediate           → investigate flagged changes/findings; fix genuine issues
5. Update the baseline (if legitimate) → AIDE --update after reviewed, intentional changes
6. Repeat                           → this is ongoing, not a one-time project
```

> **The throughline:** this entire guide is the *detection* half of the security principles introduced earlier — least privilege, defense in depth, and attack surface reduction reduce the likelihood and impact of a problem; audit logging and integrity monitoring are how you find out whether a problem occurred anyway, and prove what happened when it did.

## 💡 Best Practices

- Set up audit rules and a FIM baseline as part of initial provisioning, not retrofitted later — a baseline established on an already-compromised or already-drifted system provides false assurance.
- Watch the specific files most relevant to privilege and identity (`/etc/passwd`, `/etc/shadow`, `/etc/sudoers`, SSH config) with `auditd` — file permissions alone don't tell you *who* changed something or *when*.
- Schedule FIM checks (AIDE or equivalent) and ensure results are actually reviewed/alerted on — an unreviewed scheduled check provides little real value.
- Genuinely investigate flagged changes before updating a FIM baseline to accept them — routinely accepting flags without review defeats the tool's purpose.
- Treat OpenSCAP-generated remediation scripts as a strong starting draft, not a script to run unattended in production — review and test changes first.
- Use Lynis for frequent, lightweight checks and OpenSCAP/SCAP profiles for periodic, formal compliance verification — they serve complementary purposes rather than being redundant with each other.
- Remember that auditing and FIM are the *detection* layer — they don't replace the *prevention* layer covered in earlier guides (least privilege, firewalls, authentication hardening); both are necessary, neither is sufficient alone.
